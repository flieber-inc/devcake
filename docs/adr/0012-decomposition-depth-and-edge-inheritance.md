# ADR-0012 — Configurable decomposition depth + dependency-edge inheritance

- **Status:** accepted (2026-07-18)
- **Context:** Two coupled gaps from the depth-1 era. (1) ADR-0006 makes Projects always decompose, and the depth-1 rule then froze every child: a Project's missions could never be split again even when ONBOARD judged them compound — they parked with `DEVCAKE-SKIP` for a human. (2) A confirmed ordering hole: decomposing an issue that other missions were `blocked by` **canceled** it without transferring its edges, and the gate treats a canceled blocker as satisfied (ADR-0007) — so downstream missions dispatched while the replacement children were still pending. Nothing could repair the graph afterwards (the Mapper drops edges touching terminal missions; the port has no `remove_relation`).

## Decision

Five coupled mechanisms, all PMO-derivable (ADR-0003/0005 preserved — no local counters, no locks):

1. **Depth is PMO state.** Each child's existing machine marker gains a generation field: `devcake:decomposition:v1 parent=… manifest=… part=i/n depth={d}`. The field is optional in the parse — a marker without it is a level-1 child, provably, since the depth-1 regime could produce nothing deeper. A mission's depth is read from its **own** record only: no `DEVCAKE-CREATED` label ⇒ 0 (the app-managed label gates the read, so a forged marker in an untrusted description is inert — same trust posture as replay matching); label + marker ⇒ the recorded depth; label without a readable marker ⇒ **at-limit, fail-safe** (and children written under unlimited mode with unknown parent depth record `depth=2`, "at least one generation down", so a later finite limit still gates them). Marker reads anchor to the **last** match — the app appends the genuine footer after the untrusted Dev-authored body, so quoted markers can only precede it — and marker syntax in draft bodies is **defanged** (opening backtick stripped, pre-hash) at child creation, protecting both the depth read and the replay child-scan. Chosen over a parent-walk derivation: the walk needs kind-guessing `get`s at decision time and re-derives what the PMO can simply hold.
2. **The limit is operator policy.** `AppConfig.max_decomposition_depth` (default **2**, `0` = unlimited), a Traffic-control select in the admin panel (values outside 1/2/0, set via API, round-trip as an extra option). The at-limit predicate lives in ONE place (`markers.at_decomposition_limit`) shared by the finalizer gate and the dispatch-time rule. At/above the limit (or unknown depth), a `decomposed` outcome parks with `DEVCAKE-SKIP`, restores `backlog`, and stamps the run `handed off: decomposition depth limit` — a hand-off, not a counted attempt, because retrying cannot change depth. The gate is **replay-stable**: once child checkpoints exist, a resume finishes the wiring even if the operator lowered the limit mid-flight. Dispatch interpolates a per-mission `{decomposition_rule}` line into the ONBOARD playbook (allowed / forbidden / unlimited wording) so an at-limit Dev never wastes a run discovering the rule; operator-edited templates without the placeholder keep their stored sentence — over-restrictive at worst, and `/health` warns that the depth knob cannot reach such a template's Dev. Unlimited removes the fission backstop by explicit operator choice; the help copy and playbook wording say so plainly.
3. **Edge inheritance on issue decomposition — fail-closed.** Before the original is canceled, its dependency topology is replicated onto the children: every still-open blocker (re-read from a post-creation snapshot, honoring relations humans add mid-finalize) → each child, and each child → every still-open dependent (**all-children fan-out** — a founder decision; "blocked by the original" means "blocked by all of its replacements", and it survives a human deleting a sibling edge). Every inherited edge maps 1:1 onto an edge the original already had, so inheritance can create no new cycle. Edges are checkpointed with stable keys, duplicate-tolerant, and **strict exactly like sibling edges**: a failure audits (`relation_inherit_failed`) and aborts finalization *before* the cancel — the original stays open and keeps gating its dependents; transients heal on retry, deleted endpoints drop out of the recomputed lists, and persistent failures park the mission with ordering intact. The gate's canceled-satisfies rule therefore stays sound unconditionally — the cancel is the last checkpoint, and it is unreachable past a missing edge. Children of a decomposed issue are also created **inside its containing project** (`parent_ref` passthrough), so the ADR-0006 tracking sweep — a flat in-project filter — counts the canceled child terminal while the grandchildren hold the project open.
4. **The family gate.** The scheduler withholds any `DEVCAKE-CREATED` issue whose marker-parent is an **issue that is still open**: the parent's cancel is finalization's last step, so an open issue-parent means the child's inherited/sibling edges may not all exist yet (or the parent is parked for a human). This closes the residual window in which a freshly created child (empty `blocked_by`) could be adopted and dispatched between creation and edge wiring — including across a crash. Project parents (open by design under `DEVCAKE-TRACKING`) and parents missing from the snapshot are exempt (fail-open, pre-ADR behavior).
5. **Lineage in both directions.** Children already carried `parent=` + a human footer; the canceled original now gains a durable description note `_Decomposed by DevCake into {children keys}_` via a new minimal port capability `PMOPort.append_description(ref, text)` (append-only intent, markdown fidelity, issues-only in v0; Linear: read-current + `issueUpdate` — an unguarded RMW whose lost-human-edit window is accepted for a short footer on an issue canceled moments later). The note is **best-effort by design**: it is provenance, not ordering safety, so a failing append audits `lineage_note_failed` and never blocks the cancel or burns attempts. Note text is built from authoritative child keys (create returns + the replay scan, never a lagging snapshot), so the replay presence-guard matches across deliveries.

## Alternatives considered

- **Parent-walk depth derivation (no marker change)** — one `pmo.get` per level at decision time, needs issue-vs-project kind guessing for level-1 parents, breaks (fail-safe parks) when a human deletes the parent, and leaves depth derived rather than held by the PMO. Rejected: the PMO is the stateful holder.
- **Internal depth counter / local lineage store** — violates ADR-0003/0005 outright. Rejected.
- **Sink-children fan-out** (dependents blocked only by children no sibling waits on) — fewer Linear relations, transitively equivalent on the happy path, but a human canceling one sink releases the dependent while non-sink ancestors are open, and with no `remove_relation` the graph could never be tightened later. Rejected for v0; recorded as the relief valve if fan-out volume ever hurts (Linear's `inverseRelations` read pages at 50 — realistic decompositions stay far below).
- **Rewiring dependents by deleting the old edge** — needs `remove_relation`, and DevCake deleting human-created relations crosses a line ADR-0007 deliberately drew. Rejected; edges stay strictly additive.
- **Best-effort inherited edges** (swallow the failure, audit, cancel anyway) — the original implementation, rejected after review: a swallowed failure whose checkpoint records the step as done permanently loses the edge, and the subsequent cancel releases the dependent early — the exact hole this ADR closes, reopened on the failure path. Fail-closed keeps ordering under every failure at the cost of a loud human-recoverable park in the rare persistent-error case.
- **A `depth=` counter without last-match anchoring** — defeated by a Dev quoting its parent's footer (handed to it verbatim in the prompt); the quoted marker would shadow the genuine one and bypass the limit. Rejected in favor of last-match + body defanging.

## Consequences

- Depth-1-era missions parked with `DEVCAKE-SKIP` become decomposable after a human clears the SKIP (the label was the era's only depth record; its marker parses as depth 1 < 2).
- Off-team dependents are invisible to the team-scoped inheritance scan (managers are per-instance, ADR-0009) and keep pointing at the canceled original — exactly the pre-ADR behavior, now a documented limitation instead of a silent one. Within the team, `inverseRelations` is cursor-walked past a full page (ceiling 500, fail-loud) so a heavily-linked dependent is not silently missed.
- A persistent inherited-edge failure parks the mission `DEVCAKE-FAILED` with the original still **open** — dependents stay gated (fail-safe), children stay withheld by the family gate, and a human resolves; there is no silent-early-release state.
- A failing lineage-note append loses the note (audited `lineage_note_failed`) — hygiene, accepted; the linking feed comment still posts.
- The `decomp:tracking` cancel remains the terminal checkpoint; every new write (inherited edges, lineage note) happens before it, so crash-resume preserves the no-released-window guarantee at every prefix, and the family gate covers the child-adoption window in between.
- `test_done_or_canceled_blocker_unblocks` (the gate's canceled-satisfies rule) survives unchanged — the fix is in the finalizer plus the family gate, not the blocker rule.
